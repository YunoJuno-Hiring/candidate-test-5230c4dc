2. The frontend contract you cannot break

The frontend is "fully wired" and is not in scope. That makes its TypeScript types a hard interface specification. Read these three files before writing a line of Python: frontend/src/api/billing.ts, frontend/src/pages/Billing.tsx, frontend/src/pages/InvoiceDetail.tsx.

What the UI actually sends and reads

CallRequestResponse the UI consumes
POST /api/billing/runs/ {"month": "2026-05"} — a single string, not year+month BillingRunResult { run_id: string; invoices_generated: number; status: string }. Only invoices_generated is rendered, but return all three.
GET /api/invoices/?month=YYYY-MM query param month An array (not a paginated envelope). Only id is rendered, but send the useful summary fields anyway.
GET /api/invoices/<id>/ — Any JSON object; the page pretty-prints it with JSON.stringify. A 404 renders a dedicated "Invoice not found" state, so 404 must stay 404.
Do not do this

Do not switch to DRF generic views with default pagination. The UI does invoicesQuery.data.map(...) straight onto the response. A {count, results} envelope is a silent runtime break. Return a plain list.

Why keep APIView instead of ListAPIView

The existing codebase uses hand-rolled APIView classes with inline role checks (contracts/views.py). Matching that style keeps the diff idiomatic and avoids introducing a second, competing convention in a small codebase. The response shapes above are also easier to guarantee by hand.

3. Design decisions up front (and why)

3.1 Money is computed in Decimal, never float

daily_rate is DecimalField(max_digits=8, decimal_places=2) and hours is DecimalField(max_digits=5, decimal_places=2). Multiplying them yields four decimal places (7.50 × 600.00 = 4500.0000), so every line amount must be .quantize(Decimal('0.01')) before storage. Never round with float(); it will drift on totals and it will bite you the first time a rate is 0.1-ish.

3.2 The billing grain is Company × Freelancer × Month, and the key is a period, not a string

One invoice per (company, freelancer, month) means a freelancer working for two companies in the same month gets two invoices — correct, because the payer is the company. The natural unique key is (company, freelancer, period_start). Storing period_start as a real Date (always the 1st) rather than a "2026-05" string means:

  • the database enforces the invariant, not application code;
  • date-range queries ("invoices in Q2") work without string parsing;
  • an index on (company, period_start) serves the list endpoint directly.

Keep period_end too (last day of the month) so the invoice is self-describing and renderable without recomputing month lengths.

3.3 Idempotency: a database constraint, not a check-then-insert

A get_or_create or an if not exists check races under concurrent retries. The only reliable guard is a unique constraint, with the insert allowed to raise IntegrityError and be treated as "already done". That is the difference between idempotent and idempotent-under-load, and it is exactly the kind of thing the brief is probing.

3.4 Line items are a snapshot, not a join

Each InvoiceLineItem stores hours, daily_rate, amount and the source date copied from the timesheet entry, plus a nullable FK back to the entry. Reasons:

  • An issued invoice must never change because someone later edits a timesheet or a contract rate. That is an accounting requirement, and it is also what "model it as if you might render it to PDF later" demands.
  • The FK is kept for traceability and for the "which entries were billed" question, but it is SET_NULL so deleting a timesheet cannot cascade away invoice history.

3.5 Partial months: filter by entry date, never by contract dates

The trap

A tempting implementation is "find contracts overlapping the month, then bill them". That is wrong. The unit of billing is the approved timesheet entry, and each entry has its own date. A contract running 12 Feb – 18 Mar contributes to March only the entries dated 1–18 Mar. Filtering on TimesheetEntry.date within the period handles partial months, mid-month starts, mid-month ends, and contracts that start and end inside the same month — all with one condition and no special cases.

Contract dates are then used only for the narrative on the invoice (contract_start/contract_end) and for a sanity assertion in tests, never for selection.

3.6 Transaction boundary: commit the invoice, then send email, then record the outcome

The question "what happens if the email send fails after the invoice row is committed?" has three possible answers. Pick one deliberately:

OptionConsequenceVerdict
Send email inside the transaction DB rollback on SMTP failure, but an email may already have left the building and the transaction is held open across a network call. Worst of both worlds. Reject.
Send email after commit, no record Invoice exists, nobody knows delivery failed, no retry path. Reject.
Commit invoice → attempt send → persist delivery_status Invoice is the source of truth and always survives. Delivery is an explicitly tracked, retryable side effect. Choose this.

Concretely: wrap the invoice + line-item creation in transaction.atomic(); leave the block; then send email and write delivery_status/delivered_at/ delivery_error in a second, separate write. A failure to email must never roll back an invoice, and a failure to email must never make the run return 500 — the invoice was still created.

3.7 Invoice numbering

Give each invoice a human-readable number (INV-2026-05-0007) that is unique and derived from the period plus a per-period sequence. It is what finance will quote on the phone, and it makes the email legible. Keep the integer PK as the API identifier so the frontend's /billing/invoices/<id> route keeps working.

3.8 Email: two emails, one per recipient, plain text + HTML alternative

The brief says the company's billing_email and the freelancer. Send two separate messages rather than one with two recipients, because the two parties must not see each other's addresses in To: — that is a data-leak smell in a real product. Use EmailMultiAlternatives with a plain-text body and an HTML alternative: plain text is the fallback that always renders, HTML is what makes it look like a real invoice.

The freelancer's address comes from Freelancer.user.email — note that FreelancerSerializer deliberately does not expose it, so read it from the model, not the serializer.

3.9 Authorisation

The stubs only require IsAuthenticated. All three endpoints must be scoped to the caller: a company admin sees only their own company's invoices; a freelancer sees only their own. Reuse the existing hasattr(user, 'company_admin') / hasattr(user, 'freelancer') pattern from contracts/views.py so the codebase stays consistent. Running billing is an admin-only action and must return 403 for a freelancer.

4. Implementation steps

1 Add the models ✅

backend/billing/models.py

Replace the comment file with three models: the run, the invoice, the line item.

Why a BillingRun model at all? The endpoint returns a run_id, so something must own it. More importantly, a run record is the audit trail finance will ask for ("who ran May, when, how many invoices, did it fail?") and it is the natural home for the run-level idempotency answer. It is cheap: one table, a few columns. 
import uuid
from decimal import Decimal

from django.db import models

from accounts.models import Company, Freelancer
from contracts.models import Contract, TimesheetEntry


class BillingRun(models.Model):
    """One invocation of the monthly billing run. Audit trail + run_id."""
    STATUS_RUNNING = 'running'
    STATUS_COMPLETED = 'completed'
    STATUS_FAILED = 'failed'
    STATUS_CHOICES = [
        (STATUS_RUNNING, 'Running'),
        (STATUS_COMPLETED, 'Completed'),
        (STATUS_FAILED, 'Failed'),
    ]

    id = models.UUIDField(primary_key=True, default=uuid.uuid4, editable=False)
    period_start = models.DateField()
    period_end = models.DateField()
    status = models.CharField(max_length=10, choices=STATUS_CHOICES, default=STATUS_RUNNING)
    invoices_generated = models.PositiveIntegerField(default=0)
    invoices_skipped = models.PositiveIntegerField(default=0)
    triggered_by = models.ForeignKey(
        'auth.User', null=True, blank=True,
        on_delete=models.SET_NULL, related_name='billing_runs',
    )
    created_at = models.DateTimeField(auto_now_add=True)
    completed_at = models.DateTimeField(null=True, blank=True)

    class Meta:
        ordering = ['-created_at']

    def __str__(self):
        return f'Billing run {self.id} for {self.period_start:%Y-%m} ({self.status})'


class Invoice(models.Model):
    """One invoice per Company x Freelancer x month."""
    STATUS_ISSUED = 'issued'
    STATUS_VOID = 'void'
    STATUS_CHOICES = [
        (STATUS_ISSUED, 'Issued'),
        (STATUS_VOID, 'Void'),
    ]

    DELIVERY_PENDING = 'pending'
    DELIVERY_SENT = 'sent'
    DELIVERY_FAILED = 'failed'
    DELIVERY_CHOICES = [
        (DELIVERY_PENDING, 'Pending'),
        (DELIVERY_SENT, 'Sent'),
        (DELIVERY_FAILED, 'Failed'),
    ]

    number = models.CharField(max_length=32, unique=True)
    company = models.ForeignKey(Company, on_delete=models.PROTECT, related_name='invoices')
    freelancer = models.ForeignKey(Freelancer, on_delete=models.PROTECT, related_name='invoices')
    billing_run = models.ForeignKey(
        BillingRun, null=True, on_delete=models.SET_NULL, related_name='invoices',
    )

    # Period bounds — period_start is always the 1st. This is the idempotency key.
    period_start = models.DateField()
    period_end = models.DateField()

    # Narrative snapshot: contract dates as they were at generation time.
    contract_start = models.DateField(null=True, blank=True)
    contract_end = models.DateField(null=True, blank=True)

    subtotal = models.DecimalField(max_digits=12, decimal_places=2, default=Decimal('0.00'))
    tax = models.DecimalField(max_digits=12, decimal_places=2, default=Decimal('0.00'))
    total = models.DecimalField(max_digits=12, decimal_places=2, default=Decimal('0.00'))
    currency = models.CharField(max_length=3, default='GBP')

    status = models.CharField(max_length=10, choices=STATUS_CHOICES, default=STATUS_ISSUED)
    delivery_status = models.CharField(max_length=10, choices=DELIVERY_CHOICES, default=DELIVERY_PENDING)
    delivered_at = models.DateTimeField(null=True, blank=True)
    delivery_error = models.TextField(blank=True, default='')

    created_at = models.DateTimeField(auto_now_add=True)

    class Meta:
        ordering = ['-period_start', 'freelancer__name']
        constraints = [
            models.UniqueConstraint(
                fields=['company', 'freelancer', 'period_start'],
                name='uniq_invoice_company_freelancer_period',
            ),
        ]
        indexes = [models.Index(fields=['company', 'period_start'])]

    def __str__(self):
        return f'{self.number} — {self.company.name} / {self.freelancer.name}'


class InvoiceLineItem(models.Model):
    """A snapshot of one approved timesheet entry as billed."""
    invoice = models.ForeignKey(Invoice, on_delete=models.CASCADE, related_name='line_items')
    # SET_NULL: invoice history must survive timesheet deletion.
    timesheet_entry = models.ForeignKey(

    contract = models.ForeignKey(Contract, null=True, on_delete=models.SET_NULL)

    date = models.DateField()
    description = models.CharField(max_length=255)
    hours = models.DecimalField(max_digits=5, decimal_places=2)
    daily_rate = models.DecimalField(max_digits=8, decimal_places=2)
    amount = models.DecimalField(max_digits=12, decimal_places=2)

    class Meta:
        ordering = ['date']

    def __str__(self):
        return f'{self.date} — {self.hours}h @ {self.daily_rate}'

3 Put the billing logic in a service, not a view ✅

backend/billing/services.py (new)
Why a service module? The run has to be callable from three places: the HTTP endpoint, a future scheduled job (manage.py command), and tests. Putting it in the view makes the second impossible without faking a request. A plain function with a clear contract is also far easier to unit-test than an APIView. 
import calendar
import datetime
from collections import defaultdict
from decimal import Decimal

from django.db import IntegrityError, transaction
from django.utils import timezone

from contracts.models import TimesheetEntry

from .models import BillingRun, Invoice, InvoiceLineItem

MONEY = Decimal('0.01')


def month_bounds(month: str) -> tuple[datetime.date, datetime.date]:
    """'2026-05' -> (date(2026,5,1), date(2026,5,31)). Raises ValueError on bad input."""
    try:
        year_s, month_s = month.split('-')
        year, mon = int(year_s), int(month_s)
        start = datetime.date(year, mon, 1)
    except (ValueError, AttributeError):
        raise ValueError('month must be in YYYY-MM format')
    last_day = calendar.monthrange(year, mon)[1]
    return start, datetime.date(year, mon, last_day)


def run_billing(month: str, *, triggered_by=None) -> BillingRun:
    """Create one invoice per (company, freelancer) with approved entries in `month`.

    Idempotent: any (company, freelancer) that already has an invoice for this
    period is skipped, so re-running is safe and returns 0 new invoices.
    """
    period_start, period_end = month_bounds(month)

    run = BillingRun.objects.create(
        period_start=period_start, period_end=period_end, triggered_by=triggered_by,
    )

    # One query, filtered on ENTRY date. This is what makes partial months correct.
    entries = (
        TimesheetEntry.objects
        .filter(
            status=TimesheetEntry.STATUS_APPROVED,
            date__gte=period_start,
            date__lte=period_end,
        )
        .select_related('contract', 'contract__company', 'contract__freelancer')
        .order_by('date', 'id')
    )

    grouped = defaultdict(list)
    for entry in entries:
        grouped[(entry.contract.company_id, entry.contract.freelancer_id)].append(entry)

    created, skipped = [], 0
    for (company_id, freelancer_id), group in grouped.items():
        try:
            with transaction.atomic():
                invoice = _create_invoice(
                    run=run, group=group,
                    period_start=period_start, period_end=period_end,
                )
        except IntegrityError:
            # Unique constraint fired: another run already billed this pair.
            skipped += 1
            continue
        created.append(invoice)

    run.invoices_generated = len(created)
    run.invoices_skipped = skipped
    run.status = BillingRun.STATUS_COMPLETED
    run.completed_at = timezone.now()
    run.save(update_fields=['invoices_generated', 'invoices_skipped', 'status', 'completed_at'])

    # Delivery happens AFTER the rows are committed — see step 6.
    from .emails import deliver_invoice
    for invoice in created:
        deliver_invoice(invoice)

    return run


def _create_invoice(*, run, group, period_start, period_end) -> Invoice:
    first = group[0]
    contract = first.contract
    company, freelancer = contract.company, contract.freelancer

    invoice = Invoice.objects.create(
        number='',  # set below, needs the PK
        company=company,
        freelancer=freelancer,
        billing_run=run,
        period_start=period_start,
        period_end=period_end,
        contract_start=contract.start_date,
        contract_end=contract.end_date,
    )

    subtotal = Decimal('0.00')
    for entry in group:
        amount = (entry.hours * entry.contract.daily_rate).quantize(MONEY)
        subtotal += amount
        InvoiceLineItem.objects.create(
            invoice=invoice,
            timesheet_entry=entry,
            contract=entry.contract,
            date=entry.date,
            description=f'Professional services — {entry.date:%d %b %Y}',
            hours=entry.hours,
            daily_rate=entry.contract.daily_rate,
            amount=amount,
        )

    invoice.subtotal = subtotal
    invoice.total = subtotal + invoice.tax
    invoice.number = f'INV-{period_start:%Y-%m}-{invoice.pk:05d}'
    invoice.save(update_fields=['subtotal', 'total', 'number'])
    return invoice
Two subtleties that matter

1. IntegrityError must be caught outside the atomic() block. Once an IntegrityError has fired inside a transaction, that transaction is broken; catching it inside and continuing raises TransactionManagementError. Note the try/except is wrapped around the with, not inside it.

2. Per-pair atomicity, not whole-run atomicity. Wrapping the entire loop in one transaction means one bad pair rolls back every other invoice. Billing is a batch job; it should be resumable and partially successful. Committing per invoice also keeps transactions short, which matters once this is scheduled against a real database.

4 Render the invoice content once, and reuse it for email and detail ✅

backend/billing/emails.py (new)
Why a renderer separate from the sender? "Model it as if you might need to render it to PDF later" means the invoice content should be a pure function of the invoice row, not tangled into SMTP. A render_invoice_text(invoice) / render_invoice_html(invoice) pair can later be swapped for a PDF renderer without touching delivery. 
from django.conf import settings
from django.core.mail import EmailMultiAlternatives
from django.utils import timezone

from .models import Invoice


def invoice_recipients(invoice):
    """Company billing address + the freelancer's own address.

    FreelancerSerializer deliberately does not expose the email, so read the
    User relation directly rather than going through the serializer.
    """
    return [invoice.company.billing_email, invoice.freelancer.user.email]


def render_invoice_text(invoice) -> str:
    lines = [
        f'Invoice {invoice.number}',
        f'Period: {invoice.period_start:%d %b %Y} – {invoice.period_end:%d %b %Y}',
        f'Billed to: {invoice.company.name}',
        f'Freelancer: {invoice.freelancer.name}',
        '',
    ]
    for li in invoice.line_items.all():
        lines.append(
            f'{li.date:%d %b %Y}  {li.hours}h x {li.daily_rate} = {li.amount}'
        )
    lines += [
        '',
        f'Subtotal: {invoice.subtotal}',
        f'Total:    {invoice.total} {invoice.currency}',
    ]
    return '\n'.join(lines)


def deliver_invoice(invoice) -> None:
    """Send the invoice to both parties. Never raises — records the outcome.

    Called AFTER the invoice transaction has committed, so a failure here can
    never roll back an issued invoice.
    """
    try:
        for recipient in invoice_recipients(invoice):
            msg = EmailMultiAlternatives(
                subject=f'Invoice {invoice.number} — {invoice.period_start:%B %Y}',
                body=render_invoice_text(invoice),
                from_email=settings.DEFAULT_FROM_EMAIL,
                to=[recipient],
            )
            msg.attach_alternative(render_invoice_html(invoice), 'text/html')
            msg.send()
    except Exception as exc:  # SMTP is a network boundary
        invoice.delivery_status = Invoice.DELIVERY_FAILED
        invoice.delivery_error = str(exc)[:2000]
        invoice.save(update_fields=['delivery_status', 'delivery_error'])
        return
    invoice.delivery_status = Invoice.DELIVERY_SENT
    invoice.delivered_at = timezone.now()
    invoice.delivery_error = ''
    invoice.save(update_fields=['delivery_status', 'delivered_at', 'delivery_error'])
The answer to the transaction-boundary question, in one sentence

The invoice is committed first and is authoritative; delivery is a best-effort side effect that is recorded on the invoice (pending → sent | failed) so it can be retried, and a delivery failure is never allowed to fail the billing run.

Settings gap you will hit

config/settings.py sets EMAIL_HOST/EMAIL_PORT but not DEFAULT_FROM_EMAIL. Django falls back to webmaster@localhost, which Mailpit accepts but looks wrong. Add DEFAULT_FROM_EMAIL = config('DEFAULT_FROM_EMAIL', default='billing@yunojuno.test') as a one-line settings change and mention it in the notes. It is a genuine blocker for a legible email, not a refactor.

6 Replace the stub views ✅

backend/billing/views.py
Why keep APIView? Consistency with contracts/views.py, and it guarantees the exact response shapes the frontend expects. Note the deliberate choice to return 200 (not 201) from the run endpoint: the UI treats it as an action result, not a resource creation, and a re-run that creates zero invoices is a success, not an error. 
from rest_framework import status
from rest_framework.permissions import IsAuthenticated
from rest_framework.response import Response
from rest_framework.views import APIView

from .models import Invoice
from .serializers import InvoiceDetailSerializer, InvoiceSerializer
from .services import month_bounds, run_billing


def invoices_for_user(user):
    """Same role-branching pattern as contracts/views.py."""
    if hasattr(user, 'company_admin'):
        return Invoice.objects.filter(company=user.company_admin.company)
    if hasattr(user, 'freelancer'):
        return Invoice.objects.filter(freelancer=user.freelancer)
    return Invoice.objects.none()


class BillingRunView(APIView):
    permission_classes = [IsAuthenticated]

    def post(self, request):
        if not hasattr(request.user, 'company_admin'):
            return Response(
                {'detail': 'Only company admins can run billing.'},
                status=status.HTTP_403_FORBIDDEN,
            )
        month = request.data.get('month', '')
        try:
            run = run_billing(month, triggered_by=request.user)
        except ValueError as exc:
            return Response({'month': str(exc)}, status=status.HTTP_400_BAD_REQUEST)
        return Response({
            'run_id': str(run.id),
            'invoices_generated': run.invoices_generated,
            'invoices_skipped': run.invoices_skipped,
            'status': run.status,
        })


class InvoiceListView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request):
        qs = invoices_for_user(request.user).select_related('company', 'freelancer')
        month = request.query_params.get('month')
        if month:
            try:
                start, end = month_bounds(month)
            except ValueError as exc:
                return Response({'month': str(exc)}, status=status.HTTP_400_BAD_REQUEST)
            qs = qs.filter(period_start=start)
        # Plain list — the frontend calls .map() on the response directly.
        return Response(InvoiceSerializer(qs, many=True).data)


class InvoiceDetailView(APIView):
    permission_classes = [IsAuthenticated]

    def get(self, request, pk):
        try:
            invoice = (
                invoices_for_user(request.user)
                .select_related('company', 'freelancer')
                .prefetch_related('line_items')
                .get(pk=pk)
            )
        except Invoice.DoesNotExist:
            return Response({'detail': 'Not found.'}, status=status.HTTP_404_NOT_FOUND)
        return Response(InvoiceDetailSerializer(invoice).data)
Why period_start=start and not a range

period_start is always the 1st of the month, so equality is exact and uses the (company, period_start) index cleanly. A __range would also work but implies the column might hold other values, which the model contract forbids.

7 Register in the admin ✅

backend/billing/admin.py (new)

Every other app in this codebase has an admin.py; billing currently does not. Finance will want to look at an invoice without curl. Inline the line items, read-only.

Why the admin matters here, beyond consistency. The Billing page is the primary interface, but when an invoice looks wrong — a missing line item, a delivery that failed, an odd total — the admin is where you inspect it. Critically, it is the only place delivery_status / delivery_error are visible. We built those fields so a failed email is recoverable; without a UI they are write-only. list_filter on delivery_status turns "which invoices failed to send?" into one click — the manual half of the retry story deferred in §8.
Why line items are read-only. Line items are an immutable snapshot (§3.4). If the admin allowed editing hours or amount, you could silently corrupt an issued invoice and leave the stored subtotal/total disagreeing with the lines. can_delete = False plus readonly_fields enforces the snapshot invariant in the UI layer, not just by convention. extra = 0 because invoices are created by the billing run, never by hand.
Tightening beyond the original plan

A bare admin.site.register(BillingRun) lets a user edit an audit record — change its status, period or counters. That is wrong for the same reason BillingRun.status is system-owned (see §3.3 and the earlier discussion): a run record is evidence of what happened, not state you mutate. BillingRunAdmin below makes runs fully read-only — inspectable, not editable. 

from django.contrib import admin

from .models import BillingRun, Invoice, InvoiceLineItem


class InvoiceLineItemInline(admin.TabularInline):
    model = InvoiceLineItem
    extra = 0
    readonly_fields = ['date', 'description', 'hours', 'daily_rate', 'amount']
    can_delete = False


@admin.register(Invoice)
class InvoiceAdmin(admin.ModelAdmin):
    list_display = ['number', 'company', 'freelancer', 'period_start', 'total', 'delivery_status']

    inlines = [InvoiceLineItemInline]


@admin.register(BillingRun)
class BillingRunAdmin(admin.ModelAdmin):
    """Runs are an audit trail: inspectable, never editable."""
    list_display = ['id', 'period_start', 'status', 'invoices_generated', 'invoices_skipped', 'created_at']
    list_filter = ['status', 'period_start']
    readonly_fields = [f.name for f in BillingRun._meta.fields]

    def has_add_permission(self, request):
        return False

    def has_change_permission(self, request, obj=None):
        return False

import datetime
from django.core.management.base import BaseCommand
from billing.services import run_billing


class Command(BaseCommand):
    help = 'Run monthly billing for a given month (defaults to last month).'

    def add_arguments(self, parser):
        parser.add_argument('--month', default=None, help='YYYY-MM')

    def handle(self, *args, **options):
        month = options['month']
        if not month:
            today = datetime.date.today()
            first = today.replace(day=1)
            month = (first - datetime.timedelta(days=1)).strftime('%Y-%m')
        run = run_billing(month)
        self.stdout.write(self.style.SUCCESS(
            f'Run {run.id}: {run.invoices_generated} generated, {run.invoices_skipped} skipped.'
        ))

import datetime
from decimal import Decimal

import pytest
from django.core import mail

from billing.models import Invoice

@pytest.mark.django_db
def test_rerun_is_idempotent(admin_client, active_contract):
    TimesheetEntry.objects.create(
        contract=active_contract, date=datetime.date(2026, 5, 4),
        hours=Decimal('8.0'), status='approved',
    )

    first = admin_client.post('/api/billing/runs/', {'month': '2026-05'}, format='json')
    assert first.status_code == 200
    assert first.data['invoices_generated'] == 1

    second = admin_client.post('/api/billing/runs/', {'month': '2026-05'}, format='json')
    assert second.status_code == 200
    assert second.data['invoices_generated'] == 0
    assert second.data['invoices_skipped'] == 1
    assert Invoice.objects.count() == 1


@pytest.mark.django_db
def test_email_failure_does_not_roll_back_invoice(admin_client, active_contract, monkeypatch):
    TimesheetEntry.objects.create(
        contract=active_contract, date=datetime.date(2026, 5, 4),
        hours=Decimal('8.0'), status='approved',
    )

    def boom(*args, **kwargs):
        raise OSError('SMTP is down')

    monkeypatch.setattr('django.core.mail.EmailMultiAlternatives.send', boom)

    resp = admin_client.post('/api/billing/runs/', {'month': '2026-05'}, format='json')

    assert resp.status_code == 200
    invoice = Invoice.objects.get()
    assert invoice.delivery_status == Invoice.DELIVERY_FAILED
    assert 'SMTP is down' in invoice.delivery_error

The brief names it directly: "what happens if the email send fails after the invoice row is committed?" A test that proves the invoice survives and the failure is recorded is the single clearest demonstration that you understood the transaction boundary rather than just writing code that happens to work when SMTP is up.

7. What to write in CANDIDATE_NOTES.md

Keep it to the requested half-page–one-page. The specific points worth making:

  • Why Task B: it is the task with the most consequential failure modes (money, idempotency, transaction boundaries) and the least UI surface, so the engineering is what gets judged. It also composes cleanly with A and C later.
  • Grain: Company × Freelancer × month, enforced by a unique constraint, keyed on period_start as a date.
  • Idempotency: database constraint + IntegrityError handling, not a read-then-write check. Say explicitly that this is the difference between idempotent and idempotent under concurrency.
  • Partial months: selection is on entry date, so contract start/end dates never need special-casing.
  • Transaction boundary: invoice commits first, email is a post-commit side effect with a recorded delivery_status; a send failure cannot roll back or fail the run.
  • Snapshot vs join: line items copy hours/rate/amount so invoices are immutable history and are PDF-ready.
  • Email choice: two messages (privacy), plain text + HTML alternative.
  • The one settings change (DEFAULT_FROM_EMAIL) and why.
  • Next steps: retry/backoff for failed deliveries, a void/credit-note path, VAT, pagination on the list endpoint, PDF rendering behind the existing renderer seam, and locking the run (advisory lock or a unique "running" row per period) if two admins click simultaneously.
